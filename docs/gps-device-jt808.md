# 车载 GPS 定位器接入（JT808 / 信春科技 V1.54 低功耗版）

设备直接把定位发到本后端（不经过厂家平台、不用 Traccar），进入现有的地图 / 静止报警 / 工时 / 在线判定链路。

```
定位器 ──TCP(JT808)──▶ 后端网关 Jt808Server ──▶ GpsDeviceService.ingest
                                                    │ 设备号 → gps_devices 登记表 → 车牌
                                                    │ 车牌 → 司机接单时填的车牌 → 进行中任务
                                                    ▼
                                            GpsService.upload(driverId, taskId, 点)
                                            → gps_logs（source='device'）→ 地图/报警/工时/在线
```

代码在 `backend/src/gps-device/`：`jt808.codec.ts`（协议编解码，纯函数，测试用厂家报文样例逐字节比对）、
`jt808.server.ts`（TCP 网关）、`gps-device.service.ts`（设备 ↔ 车牌 ↔ 任务）、`gps-device.controller.ts`（管理接口）。
Web 管理端菜单「GPS设备」（管理员 / 调度员）。

## 1. 后端环境变量

| 变量 | 说明 |
|---|---|
| `JT808_PORT` | 网关监听的 TCP 端口，如 `5023`。**不设置则网关不启动**。 |
| `JT808_DEVICE_TZ_OFFSET_HOURS` | 设备上报时间的时区，默认 `8`（厂家协议用北京时间）。设备开机会发 0x1007 时区同步，收到后以设备为准。 |

## 2. 数据库

服务启动时会自动执行幂等 DDL（`gps-device.schema.ts`）补齐 `gps_logs.source` 列和 `gps_devices` 表，
**不需要手工先跑 SQL**，部署顺序也就不会影响线上。

如果数据库账号没有 DDL 权限，启动日志会出现
`Schema check failed, run database/migrations/... manually`，这时在 Supabase SQL Editor 手工执行一次：

```
database/migrations/2026-09-14_gps_devices.sql
```

## 3. Railway 暴露 TCP 端口

Railway 的 HTTP 域名只转发 HTTP，设备走原始 TCP，需要 **TCP Proxy**：

1. Railway → 后端 service → **Settings → Networking → TCP Proxy → Add**
2. 内部端口填 `JT808_PORT` 的值（如 `5023`）
3. Railway 会分配一个 `xxx.proxy.rlwy.net:NNNNN` 形式的 **域名 + 端口** —— 这就是要写进设备的服务器地址
4. Variables 里加 `JT808_PORT=5023`（以及可选的 `JT808_DEVICE_TZ_OFFSET_HOURS`）
5. ⚠️ **Variables 里必须再显式加一个 `PORT`**，值取服务域名的 target port（本项目是 `8080`，
   在 Railway → Settings → Networking 的域名那一行能看到）。
   加了 TCP Proxy 之后 Railway 会把 `PORT` 自动顶成 TCP 目标端口（5023），HTTP 服务就会和网关抢同一个端口：
   网关先启动占住 5023，随后 `app.listen` 报 `EADDRINUSE`，**整个后端崩溃重启循环、API 全线 502**。
6. 重新部署，日志应同时出现
   `JT808 gateway listening on 0.0.0.0:5023` 和 `Local: http://localhost:8080`

每个 service 只能有一个 TCP Proxy。同一服务可以同时跑 API 和 TCP 网关，但两个端口必须不同，
且 `PORT` 必须显式写死。代码里也加了兜底：两个端口相同时只关掉网关、不拖垮 API，设备页会显示网关未运行。

## 4. 设备侧配置（发给厂家的信息）

厂家远程改设备服务器地址时，把 Railway 分配的**域名 + 端口**发给他们。

**本项目已开通，实际参数如下（2026-09-21 建立）：**

```
服务器地址（域名）：iriguchi.proxy.rlwy.net
端口：18239
协议：JT/T 808-2013（设备默认即是，参数 0xF156 不用改）
```

对应后端内部监听端口 `JT808_PORT=5023`（Railway TCP Proxy 把公网 18239 转发到容器内 5023）。

⚠️ **必须用域名，不要用 IP。** 协议参数 `0x0013` 明确写的是「主服务器地址，IP 或域名」，域名完全支持；
而 Railway 的 TCP 代理只保证域名稳定，背后的 IP 会变——写死 IP 过一段时间就会全部掉线。
如果厂家的工具只能填 IP，需要改用固定 IP 的服务器，或自备域名 CNAME 到该代理域名（Railway 文档 Custom domain for TCP proxying，端口仍用 Railway 给的）。

设备接车电（ACC/常电）安装；SIM 卡需 4G 数据，NZ 频段含 B28。

## 5. 登记与绑定流程（Web 端「GPS设备」页）

1. 设备开机连上网关后，因未登记会被拒绝注册，页面顶部会显示 **「有未登记的设备正在尝试连接」** 和它的设备号
2. 点设备号 → 填**车牌** → 登记。之后设备重新注册即被接受（设备自己会重试）
3. 司机接单时填写的车牌**必须与登记车牌一致**（不区分大小写、空格、连字符），定位点才会归到该司机的进行中任务
4. 没有进行中任务时，设备位置只更新在设备列表（最后位置 / 电量 / 在线），不写轨迹

页面操作：**立即定位**（0x8201）、**实时模式**、**重启**（0x8155）、停用 / 删除。

页面还会显示：
- **离线提醒**：顶部红色卡片列出「哪些车的设备不在线」（车牌 + 设备号 + 离线多久），仪表盘也有一张「设备离线」统计卡
- **当前任务**：每台设备当前挂在哪个司机的任务上。设备在线、车在跑却显示「无进行中任务」，基本就是司机接单时车牌输错了
- **SIM 卡 ICCID**：哪张卡装在哪台设备、哪辆车上。设备上线后自动上报（0x1107 / 0x0107 终端属性 / 定位附加 0xEB 子项 0x00B2，三处任一）并以设备为准；换了本地卡也可以照卡上印的号码手填。中国移动的 ICCID 含字母，所以按 20 位十六进制字符存，不当纯数字。换卡会在后端日志里记一条 `SIM changed`

司机端接单填车牌时，会把已登记的车牌列成按钮直接点选（仍可手输，开别的车不受影响）。

### 实时模式（调度地图需要）

低功耗版设备默认静止后会休眠、停止上报。「实时模式」一次性下发（0x8103，按厂家 2011 版布局）：
禁止休眠（`0xF117=0`）、定时 10 秒上报（`0xF115`、`0x0029`）、静止也上报（`0xF154=1`）、心跳 60 秒（`0x0001`）、设备时区（`0xF142`）。
接车电时功耗无所谓；新设备登记后建议立刻下发一次。

## 7. 安全边界与已知取舍

JT808 协议本身没有真正的身份认证：**设备号既是身份、又是鉴权码**，明文传输、无加密。这是协议和厂家固件决定的，不是实现问题。我们能做的是缩小影响面，已经做的：

- 未登记的设备号一律拒绝；一条连接上连续被拒 5 次就断开（挡设备号扫描）
- **连接槽位按可信度淘汰**：满员时先踢「从没对上设备号」的连接，再踢「对上了但不是在册设备」的，
  已登记设备的连接绝不主动踢。以前只踢「一帧都没发过」的连接，攻击者每条连接发一帧合法心跳
  就能永久占位，500 个槽位占满后真实车辆全部被拒——整个车队从地图上消失
- 发了帧却始终没对应上在册设备的连接，60 秒后回收
- **协议层错误（加密位、非法分包头）限流并计数**，超过 20 次断开。这两条路径在设备核验之前就返回，
  拒绝计数管不到它们，不限流的话一条连接能无限刷日志（每 64KB 入站约 4600 行），
  日志写入的背压会把内存顶爆，进而把同进程的 HTTP API 一起带走
- **分包缓冲按可信度分配额度**：未建立信任的连接只有 1 组 / 32KB，在册设备照旧 4 组 / 128KB。
  重组要在设备核验之前分配内存，不限额的话 500 连接 × 4 组 × 128KB ≈ 270MB 全是陌生人可控的
- 分包组数超限时丢最旧的一组并记录「这些点已应答 OK、找不回来了」，而不是把几组一起清空
- 缓冲上限在拼接之前判定（避免一字节一字节喂造成 n²/2 的内存拷贝）；连接销毁后不再处理剩余排队帧
- 一条连接中途换设备号直接断开（真实终端不会这样，只有扫描/顶号才会）
- 单帧大小、批量点数、设备缓存、待处理队列都有上限（批量点数超限时会记一条 warn，说明丢了多少、且已应答 OK 找不回来）
- 只有设备标记为「盲区补报」的批量包才允许带旧时间戳；实时点超过 5 分钟偏差一律按服务器时间入库并告警
- 同一车牌同时挂多个进行中任务时**不猜**，不归属，避免把 A 车位置画进 B 的任务
- `set_server`（能把设备迁走）仅管理员可下发，主机名/端口做了校验
- 上传的图片**按文件内容判定类型**，扩展名和 Content-Type 都由服务端自己决定（客户端给的一律不采信），
  单张 10MB、最多 5 张。否则司机账号能把 `.html` / `.svg` 存进存储桶，用公司域名做钓鱼页；
  走本地存储兜底时那是和 API 同源提供的，等于存储型 XSS

**刻意没做的，以及原因：**

| 没做 | 原因 |
|---|---|
| 要求先注册/鉴权才接受定位 | 鉴权码就是设备号，攻击者先发一条注册即可通过，安全收益为零；反而可能把跳过注册的固件挡在门外 |
| 同设备号第二个连接拒绝接入 | 设备休眠/换基站后重连非常频繁，旧连接常是半死的 TCP；拒绝新连接会把**真实车辆**锁在外面。现在仍是新连接顶掉旧的，但旧连接 60 秒内还活跃时会打警告日志 |
| 按 IP 限流 / IP 白名单 | Railway 的 TCP 代理不透传客户端 IP，所有设备和攻击者共用一个来源 IP，按 IP 限流等于全车队共享一个桶，只会误伤 |
| 用独立的 `received_at` 列驱动在线判定和报警 | 实时点已被钳制在服务器时间 ±5 分钟内，等价效果；改动会碰到刚调稳的静止报警逻辑，留作后续 |
| 全局接口限流 | 手机客户端常共用运营商 NAT 出口 IP，贸然开全局限流会误伤真实司机 |
| 把工完照片的存储桶改成私有 + 签名 URL | 需要改成「存对象路径、读取时现签 URL」，`work_records.imageUrls` 里已经存的公开地址要迁移，网页端和司机端的渲染也要跟着改。**当前状态：桶是公开的，拿到 URL 的人就能看工地照片，且永久有效**（URL 本身是 UUID，猜不到，但一旦外泄就收不回）。要做的话单独排一次 |

**残余风险**：知道某个设备号的人，可以连上网关伪造该车位置、或把该车顶下线。对 10 台车的车队、端口不公开的情况下风险可接受；真出现异常，日志里会有 `taken over by ... while the previous connection was still active` 和被拒次数告警。

**值得盯的日志**（出现即代表有人在打这个端口）：
`connection limit reached, dropping an untrusted connection`、
`protocol errors on one connection ... closing`、
`never matched a registered device, closing`、
`dropping an incomplete subpackage set ... already acked OK and are lost`。

## 8. 排错

| 现象 | 看什么 |
|---|---|
| 页面显示「网关未启动」 | 后端没设 `JT808_PORT`；或 `JT808_PORT` 与 `PORT` 相同（见 §3 第 5 条），日志有 `same as the HTTP port` |
| API 全线 502、后端反复重启 | 日志搜 `EADDRINUSE`。多半是 `PORT` 没显式设置，被 TCP Proxy 顶成了 `JT808_PORT` |
| 设备一直不出现在「未登记」里 | 设备服务器地址 / 端口没改对；Railway TCP Proxy 端口与 `JT808_PORT` 不一致；SIM 无数据 |
| 已登记但地图不显示 | 车牌与司机接单填写的不一致；或该司机没有进行中任务（看设备列表的「最后位置」是否在更新） |
| 时间差 8 小时 / 12 小时 | 检查 `JT808_DEVICE_TZ_OFFSET_HOURS`，或下发一次实时模式（会同步设备时区） |
| 设备在线但无定位 | `no_fix`：室内 / 天线遮挡，设备列表里电量、信号仍会更新 |

协议细节以 `jt808.codec.spec.ts` 里的厂家样例为准；设备识别用消息头里的 11 位设备号（0x0100 里的终端 ID 字段是固定值，勿用）。

# 附:RUC 路税提醒(新西兰)

RUC 按**里程**购买:一张许可覆盖到某个里程读数,车辆跑过那个读数之前必须续买,超出继续行驶会被处罚。
所以系统盯的是「**还剩多少公里**」,不是到期日期。

管理端菜单:**车辆/路税**。

## 怎么用

1. **登记车辆** —— 车牌必须与定位器登记、司机接单填写的一致(三处同一口径,自动忽略大小写空格连字符)
2. **校准里程** —— 填车上 hubodometer 的实际读数。这是系统里程的基准,建议每月做一次
3. **登记许可** —— 买到 RUC 后,把许可上的起止里程填进来。保存后提醒重新开始计算

之后系统每天早上检查一次,里程由车载定位器上报自动累加。

## 提醒分级

| 级别 | 触发 | 含义 |
|---|---|---|
| 正常 | 剩余充足 | 不推送 |
| 需安排购买 | 剩余 < 500 km,**或**按最近一周用量预计 3 天内用完 | 安排购买 |
| 即将用完 | 剩余 < 200 km | 尽快 |
| 已超出许可 | 剩余 ≤ 0 | 违规行驶,立即处理 |
| 未登记 | 没有许可记录 | 界面显示,但不推送(避免没录入的车天天报警) |
| **需校准** | 登记了许可、但从没录过 hubodometer 读数 | 推送一次,提醒去做「校准里程」。这辆车算不出剩余里程,不提醒的话会一路跑到超里程被罚 |

同一级别**只推送一次**,升级了才再推;登记新许可后重新计。阈值在系统设置里改(`ruc_warn_km` / `ruc_critical_km` / `ruc_warn_days`)。
做完一次校准后提醒级别归零,正常分级重新生效。

每天早上 8 点检查一次,按**新西兰时间**(容器时区锁在 `Pacific/Auckland`;之前跑 UTC 时这个提醒实际落在当地晚上 9 点)。

## ⚠️ 里程是估算值

法定依据是车上的 hubodometer 读数,系统里的里程是**按定位器上报累加的估算**,用于提前提醒。

- 优先用定位器自己的里程计;没有则用两点间 GPS 距离兜底
- 计数器倒退(换设备)或一次跳变过大,只重置基准,不污染估算
- 从没校准过的车不会凭空生成读数,状态显示「未登记/从未校准」
- 校准**允许往小改**:估算值可能偏高(GPS 兜底会多算、换过设备、上次手滑多打一位),
  而校准存在的意义就是纠正它。以前拿估算值当下限拦着,输错一次这辆车就永久锁死了

**买 RUC 时务必以车上实际读数为准。** 界面上会显示「N 天前校准」,超过 30 天会变黄提醒重新校准。

## 不做自动购买

自动扣费购买 RUC 需要成为 NZTA 认证的**电子里程记录器(eRUC)**服务商,那是一套资质认证流程,不是代码能解决的。
本功能只做提醒,购买仍在 NZTA 或代理处办理。
